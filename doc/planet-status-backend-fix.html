PLANET STATUS / BACKEND FIX

天体状态接口
后端修复方案

为太阳与八大行星分别返回一条明确状态，并确保查询失败时返回错误响应。

GET/v1/planet/status
2 份完整替换文件固定 9 条状态512 种组合验证通过文档方案 · 手动实施

用数据库结果建立索引，用固定名称列表生成响应。 每个名称只追加一次；业务层包装查询错误，控制器对所有错误统一结束处理。

完整代码已添加结构体、字段和方法注释。
01 / PROBLEM

两处需要修复的逻辑

状态列表在比较过程中不断追加

现有 biz.Planet.ShowStatus() 在内层循环遇到一个名称不同的元素时，就追加一条 Exist: false 的状态。只与一个元素不匹配，不能证明整个结果中没有该天体。新追加的元素还会被后续外层循环继续遍历，导致大量重复项。

当数据库为空时，planets 也是空的，内层循环根本不会执行，于是九个尚未创建的天体全部遗漏。已有多个天体时，还可能同时返回同一个名称的 true 和 false。

原实现的复现结果
测试数据原结果修复后应有的结果
空表0 条状态9 条，全部为 false
只有 Sun256 条状态9 条，只有 Sun 为 true
Sun、Earth288 条；Earth 同时有 true / false9 条，仅 Sun、Earth 为 true

原实现的数量来自隔离测试；检查时，本机 MySQL 只有 Sun，也通过只读查询复现了 256 条结果。

查询错误没有被控制器识别，继续返回成功

现有模型和业务层直接返回数据库原始错误，而控制器只处理 *sys_error.DatabaseError。errors.As() 只会沿错误链查找指定类型，不会自动把原始错误包装成这个类型。匹配失败后，原控制器继续执行 Success()，把查询失败变成了业务码 200 和空数组。

正确区分两种情况：查询成功但没有记录应返回九条 false；查询失败应返回错误业务码，不能据此判定所有天体都不存在。

02 / APPROACH

固定输出顺序，统一错误出口

01 · 查询记录一次查询获取已创建的天体。
→
02 · 按名称建索引map[string]*model.Planet 提供名称查找。
→
03 · 遍历固定列表每个名称只输出一条状态。

最终列表始终按 Sun → Mercury → Venus → Earth → Mars → Jupiter → Saturn → Uranus → Neptune 排列。只按键查找 map，不遍历 map 生成响应，因此不依赖数据库行顺序或 map 的遍历顺序。

手动替换的文件具体修改
biz/planet.go按名称建立查询结果索引，生成九条唯一状态；将查询错误包装为 DatabaseError。
controller/v1/planet/planet.go识别数据库错误，为其他错误提供内部错误响应；所有错误分支都及时 return。

方案直接使用现有 model.Planet.FindByNames()、响应 DTO、RespBody 和 sys_error 类型。路由仍由 v1.GET("/planet/status", planet.ShowStatus) 注册，完整路径包含 /v1 前缀。

现有 planet.name 唯一索引和 GORM 的单数表名配置可继续使用；实现代码不新增依赖或配置项。

03 / BUSINESS

业务层：每个天体生成一次

下面是 biz/planet.go 的完整替换内容。保留现有业务实体、字段和 fillByORM(ctx, record) 方法形式。

替换完整文件biz/planet.go 
package biz

import (
	"SolarNotesAdminAPI/model"
	"SolarNotesAdminAPI/sys_error"
	"context"
	"errors"
)

// names 定义太阳与八大行星的匹配标识,并决定状态列表的返回顺序。
var names = [9]string{
	"Sun",
	"Mercury",
	"Venus",
	"Earth",
	"Mars",
	"Jupiter",
	"Saturn",
	"Uranus",
	"Neptune",
}

// Planet 本结构体用于表示星球业务实体
type Planet struct {
	ID    int64  // ID 行星的唯一标识符
	Name  string // Name 行星名称 (用于前台前端匹配3D资源)
	Title string // Title 行星标题
	Intro string // Intro 行星简介
	Exist bool   // Exist 行星是否存在 (用于判定能否创建该天体)
}

// ShowStatus 查询已创建的天体,按 names 的顺序返回恰好九条状态。
// 数据库中没有记录的天体仍然返回,其 Exist 为 false。
// 查询失败时返回 DatabaseError,由控制器决定错误响应。
func (p *Planet) ShowStatus(ctx context.Context) ([]*Planet, error) {
	if p == nil || ctx == nil {
		return nil, &sys_error.InternalError{
			Cause: errors.New("nil planet entity or context"),
		}
	}

	// planetNames 用作数据库查询条件,并保留固定的输出顺序。
	planetNames := make([]string, 0, len(names))
	for _, name := range names {
		planetNames = append(planetNames, name)
	}

	orm := &model.Planet{}
	records, err := orm.FindByNames(ctx, planetNames)
	if err != nil {
		return nil, &sys_error.DatabaseError{Cause: err}
	}

	// recordsByName 只负责查找记录,最终输出仍由 planetNames 驱动。
	recordsByName := make(map[string]*model.Planet, len(records))
	for _, record := range records {
		if record == nil {
			return nil, &sys_error.InternalError{
				Cause: errors.New("nil planet record"),
			}
		}
		recordsByName[record.Name] = record
	}

	// 每个预定义名称只追加一次,空表也会得到九条 Exist=false 的状态。
	planets := make([]*Planet, 0, len(planetNames))
	for _, name := range planetNames {
		planet := &Planet{
			Name:  name,
			Exist: false,
		}
		record, exists := recordsByName[name]
		if exists {
			planet.fillByORM(ctx, record)
			planet.Exist = true
		}
		planets = append(planets, planet)
	}

	return planets, nil
}

// fillByORM 将数据库字段填充到当前业务实体,Exist 由调用方明确设置。
// 保留当前工程的 context 参数形式,本方法暂不使用该参数。
func (p *Planet) fillByORM(ctx context.Context, record *model.Planet) {
	if p == nil || record == nil {
		return
	}

	p.ID = record.ID
	p.Name = record.Name
	p.Title = record.Title
	p.Intro = record.Intro
}

这段实现如何覆盖边界情况

  • 空表：查询成功后索引为空，固定名称列表仍会完整执行，因此得到九条 false。
  • 部分已创建：用名称查找记录，只把命中的天体设为 true，其他天体各返回一条 false。
  • 全部已创建：九个名称都命中，各返回一条 true。
  • 查询失败：立即返回 DatabaseError，保留 Cause，不生成不可靠的状态。
  • 异常空指针：无效实体、空 context 或异常的空记录返回 InternalError；填充方法也保留判空保护。

recordsByName 表示“本次查询中找到的记录”；planets 表示“接口需要输出的完整状态集合”。生成输出时遍历的是 planetNames，不是正在追加的结果切片。

04 / CONTROLLER

控制器：任何错误都结束处理

业务层负责查询和状态判定，控制器负责将结果填入响应 DTO，并按已有响应格式返回。

替换完整文件controller/v1/planet/planet.go 
package planet

import (
	"SolarNotesAdminAPI/biz"
	respPlanet "SolarNotesAdminAPI/param/resp/v1/planet"
	"SolarNotesAdminAPI/resp_body"
	"SolarNotesAdminAPI/sys_error"
	"errors"
	"net/http"

	"github.com/gin-gonic/gin"
)

// ShowStatus 处理 GET /v1/planet/status,调用业务层并组装天体状态响应。
// 沿用 HTTP 200 + JSON 业务码约定;出现错误后必须结束当前处理。
func ShowStatus(c *gin.Context) {
	respBody := &resp_body.RespBody{}
	planetBiz := &biz.Planet{}
	planets, err := planetBiz.ShowStatus(c.Request.Context())
	if err != nil {
		var dbErr *sys_error.DatabaseError
		if errors.As(err, &dbErr) {
			// 业务层已包装查询错误;errors.As 只负责识别错误类别。
			respBody.DBError(err)
		} else {
			// 为其他错误返回统一消息,不直接暴露底层错误内容。
			respBody.InternalError(&sys_error.InternalError{Cause: err})
		}

		// 所有错误分支统一响应并返回,不会继续组装成功数据。
		c.JSON(http.StatusOK, respBody)
		return
	}

	// 响应 DTO 只包含接口需要的 name 和 exist,不直接序列化业务实体。
	resp := &respPlanet.ShowStatusResp{
		Planets: make([]*respPlanet.ShowStatusPlanetResp, 0, len(planets)),
	}

	for _, planet := range planets {
		planetResp := &respPlanet.ShowStatusPlanetResp{
			Name:  planet.Name,
			Exist: planet.Exist,
		}

		resp.Planets = append(resp.Planets, planetResp)
	}

	data := map[string]interface{}{
		"planets": resp.Planets,
	}
	respBody.Success(data)

	c.JSON(http.StatusOK, respBody)
}

为什么把响应和 return 放到错误分支末尾

进入 if err != nil 后，先决定是数据库错误还是其他内部错误，再统一执行 c.JSON() 和 return。这样即使以后业务层增加新的错误类型，也不会落入成功响应逻辑。

数据库分支通过 errors.As(err, &dbErr) 判断类别，向 DBError() 传递原始业务错误 err。本方案中它已经由业务层包装为 DatabaseError，其 Error() 返回现有的统一数据库错误消息，底层原因保留在错误链中。

其他错误先包装成 sys_error.InternalError，再交给 respBody.InternalError()。当前响应方法读取传入错误的 Error()，这样返回的是统一内部错误消息，避免把原始底层错误直接写入响应。

沿用工程约定：HTTP 状态码仍为 200；是否成功由 JSON 中的业务 code 判断。业务码 500 在这里不是 HTTP 状态码。
