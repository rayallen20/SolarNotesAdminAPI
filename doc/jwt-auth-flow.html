FRONTEND ↔ BACKEND / AUTHENTICATION

JWT 鉴权
前后端如何通信

浏览器登录以后，为什么不必在每次请求中重新发送密码？后端又如何判断这个请求属于谁、能做什么？从一枚令牌的签发与使用开始理解。

适合初次接触 JWT以浏览器 + Gin API 为例更新：2026-11-08

登录时，后端验证账号密码并签发令牌。之后，前端随请求携带令牌，后端在每次请求中校验令牌，再决定是否允许执行业务操作。

示例范围：本文采用自有前端与自有 API 的设计示例，使用 Bearer 访问令牌，并介绍可选的刷新机制。当前仓库已有 Gin 与 CORS 中间件，尚无登录、JWT 或刷新接口；文中的路径、返回字段和时长是建议约定，不代表已实现功能。JWT 是令牌格式，本身不规定登录接口，也不等同于 OAuth 2.0。

01 / CONCEPT

JWT 是携带声明的令牌

JWT 全称为 JSON Web Token。后端可以把用户标识、签发方、使用对象和有效期等信息写成 JSON 声明，再对它们进行签名或完整性保护。接收方验证通过后，才可按约定使用这些声明。RFC 7519 §3 ↗

身份认证：你是谁？

登录时验证账号密码；后续请求通过有效令牌确定用户身份，例如用户 ID 为 1001。

权限校验：你能做什么？

确定身份后，仍需判断用户能否编辑文章、删除目录，或操作这条具体记录。

常见的签名型 JWT（JWS 紧凑格式）由三个部分组成，中间用英文句点连接：RFC 7515 §3.1 ↗

Header.Payload.Signature
部分内容理解方式
Header / 头部如 {"alg":"HS256","typ":"JWT"}声明算法与类型；后端仍须按自己的配置限制可接受算法。
Payload / 载荷如 sub、iss、aud、exp声明“主体是谁、由谁签发、给谁使用、何时失效”。
Signature / 签名段使用密钥对前两段的编码结果进行完整性保护后端据此验证内容是否被改动，以及是否由受信任的密钥持有方生成。

以 HS256 为例，可以把其计算方式理解为：RFC 7518 §3.2 ↗

签名输入 = base64url(header) + "." + base64url(payload)
签名段   = base64url(HMAC-SHA256(服务端密钥, 签名输入))
JWT      = 签名输入 + "." + 签名段

HS256 使用共享密钥生成和验证 MAC，通常统称为“签名”；RS256 则使用私钥签名、公钥验签。浏览器无需持有签发密钥。HS256 的密钥、RS256 的私钥都不能放进前端代码。

联系前面的哈希与加密：MD5 是无密钥哈希；HS256 使用带密钥的 HMAC；Base64URL 只是编码。常见签名型 JWT 的前两段可以被解码阅读，签名不会隐藏内容，因此不要把密码或其他秘密放进 Payload。JWT 也有加密形式 JWE，本文讲解的是常见的三段式 JWS。

下面把登录和一次受保护接口访问放在一起。图中的数据库负责用户、密码哈希和业务数据；后端通常可以在本地完成 JWT 的密码学校验。

03 / LOGIN

登录：用账号密码换取访问令牌

  1. 前端提交凭据。用户输入账号密码，浏览器通过 HTTPS 向登录接口发送请求。
  2. 后端认证用户。按账号查询用户，以密码哈希验证函数校验密码，同时检查账号是否禁用。数据库保存密码哈希，登录时无需还原密码。
  3. 后端构造并签发 JWT。写入用户 ID、签发方、受众、有效期等声明，再用服务端密钥生成签名。
  4. 前端接收令牌。把访问令牌保存在选定位置，之后访问受保护接口时携带它。

密码存储应使用 Argon2id 等专门的密码哈希方案；已有 bcrypt 系统可按其约束维护。把密码做一次 MD5，不能替代密码存储方案，也不能替代 HTTPS。OWASP 密码存储 ↗

请求 · 浏览器 → API
POST /auth/login HTTP/1.1
Host: api.example.com
Content-Type: application/json

{"username":"alice","password":"<用户输入的密码>"}
响应 · API → 浏览器
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: no-store

{
  "access_token": "<后端签发的完整 JWT>",
  "token_type": "Bearer",
  "expires_in": 900,
  "user": { "id": "1001", "username": "alice" }
}

expires_in: 900 表示本例访问令牌有效 900 秒，即 15 分钟。这是应用选择，并非 JWT 规定。登录失败可约定返回 401 和统一的“账号或密码错误”，前端展示错误提示即可，不会收到有效访问令牌。

JWT 内部的声明可以长这样

{
  "sub": "1001",
  "iss": "https://api.example.com",
  "aud": "solar-notes-admin-api",
  "iat": 1900000000,
  "exp": 1900000900,
  "jti": "<本次令牌的唯一标识>"
}

sub 是用户主体，iss 是签发方，aud 是允许使用该令牌的服务，iat 是签发时间，exp 是过期时间，jti 可用作撤销等机制的索引。时间采用 Unix 时间戳，单位为秒；上面是固定演示值，实际签发时使用当前时间。RFC 7519 §4.1 ↗

用户 ID 用字符串表示很合适。本项目使用 int64 雪花 ID，把这类 ID 直接作为 JavaScript Number 传输可能丢失精度；JWT 的 sub 本来也应为字符串。JWT 的这些声明由应用约定选择；本文约定必须签发并校验 exp、iss、aud 和有效的 sub。

04 / VERIFY EVERY REQUEST

访问接口：携带令牌，由后端做决定

后续请求不必重复携带密码。前端把完整访问令牌放进请求头，Bearer 与令牌之间有一个空格。这里的 Bearer 表示“持有令牌即可使用”，因此令牌本身也是凭据。不要把它放进容易进入历史记录或日志的 URL。RFC 6750 §2.1 ↗

GET /api/articles HTTP/1.1
Host: api.example.com
Authorization: Bearer <完整访问令牌>

后端中间件在进入业务前做什么？

  1. 提取令牌。检查 Authorization 的格式、是否缺失、长度是否在限制内。
  2. 限制算法并验证签名。选择服务端信任的密钥与算法，通过成熟 JWT 库验证；不能只相信令牌头里的 alg，也不能仅仅 Base64URL 解码就放行。
  3. 验证声明。按本应用规则要求并验证 exp、iss、aud、sub；存在 nbf 时确认已到生效时间。只允许有限、明确的时钟偏差。
  4. 应用会话规则。如果系统支持立即撤销、账号封禁或令牌版本，查询相应共享状态。纯粹本地验签不会自动发现这些变化。
  5. 传递可信身份。把验证后的用户 ID 放进 Gin 上下文，供业务处理器使用。用户提交的 user_id 或前端声称的角色不能替代这一步。
  6. 校验具体权限。判断该用户能否执行动作，以及能否操作这条文章或目录。然后才查询或修改允许访问的数据。

签名、算法、受众和签发方检查共同建立信任；“成功解码”只说明字符串可以读取。JWT 库的默认选项各不相同，应用必须明确配置自己要求的声明。RFC 8725 §3 ↗

结果HTTP 状态前端如何处理
身份有效，权限满足200 OK使用返回的数据；创建等操作也可能返回 201、204。
令牌缺失、过期、签名错误或已撤销401 Unauthorized按约定尝试刷新一次或重新登录；401 不一定意味着过期。
身份有效，但权限不足403 Forbidden提示没有操作权限，不要因 403 反复刷新令牌。
 
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer error="invalid_token"
Content-Type: application/json

{"code":"ACCESS_TOKEN_EXPIRED","message":"访问令牌已过期"}

这是“过期”这一具体情况的响应示例。本文的 JSON 业务码由应用自定义；Bearer 的挑战头和 invalid_token 含义见 RFC 6750 §3。无凭据请求通常只返回 Bearer 挑战，不必暴露详细错误。为隐藏特定资源是否存在，有些业务也会对无权访问的资源返回 404。

    06 / TOKEN LIFECYCLE

    过期、刷新与退出登录

    最基础的方案：访问令牌过期后要求重新登录。若希望用户保持会话，可额外设计刷新令牌。刷新不是 JWT 自带能力，必须由后端实现相应接口和会话规则。

    Access Token / 访问令牌

    示例为短期 JWT，有效期 15 分钟。前端放进 Authorization，请求业务接口。

    Refresh Token / 刷新令牌

    示例为高熵随机字符串，有效期 7 天，无需采用 JWT 格式。仅向刷新或退出接口发送，用于换取新访问令牌。

    登录时额外设置刷新 Cookie

    本文示例把 Access Token 放在前端内存，把 Refresh Token 放在 API 通过响应头设置的 HttpOnly Cookie。以下以前端 https://admin.example.com、API https://api.example.com 的同站点、跨源部署为例。

    HTTP/1.1 200 OK
Set-Cookie: refresh_token=<随机刷新令牌>; HttpOnly; Secure; SameSite=Strict; Path=/auth; Max-Age=604800
Cache-Control: no-store
Content-Type: application/json

{"access_token":"<访问 JWT>","token_type":"Bearer","expires_in":900}

    HttpOnly 阻止 JavaScript 直接读取该 Cookie；Secure 限定 HTTPS；Path=/auth 使它匹配刷新与退出路径。浏览器按 Cookie 规则保存、发送，不需要前端读取后再复制到请求头。它仍可能随 JavaScript 发起的请求发送，HttpOnly 不会阻止所有 XSS 后果。MDN Set-Cookie ↗

    访问令牌过期后的通信

    1. 业务接口返回 401。前端识别约定的可刷新情形，暂停当前请求。
    2. 前端向 POST /auth/refresh 发请求，跨源 Fetch 使用 credentials: "include"，由浏览器附带刷新 Cookie。
    3. 后端检查请求来源及 CSRF 防护，验证刷新令牌未过期、未撤销，并检查会话与账号状态。
    4. 刷新成功后返回新 Access Token，同时轮换 Refresh Token：旧值失效，通过 Set-Cookie 设置新值。服务端的失效与替换应原子完成。
    5. 前端更新内存中的 Access Token，以新令牌重试原业务请求最多一次。刷新被拒绝时清理登录状态并要求重新登录；网络故障应单独处理。
    POST /auth/refresh HTTP/1.1
Host: api.example.com
Origin: https://admin.example.com
Cookie: refresh_token=<浏览器自动附带的刷新令牌>

→ 成功：200 + 新 access_token + Set-Cookie 设置新 refresh_token
→ 凭据失效：本应用约定 401 + REFRESH_TOKEN_INVALID

    上面的 401 是本文自定义刷新接口的约定。若接入标准 OAuth 令牌端点，应遵循该端点的错误协议，不能直接套用这份自定义响应。

    轮换时保存令牌之间的关联，可检测旧刷新令牌被再次使用，并按策略撤销该会话的令牌链。这个设计借鉴 OAuth 安全最佳实践；JWT 格式本身不管理刷新。RFC 9700 §4.14 ↗

    并发与页面刷新：同一页面多个接口同时返回 401 时，应共用一个正在进行的刷新任务，避免反复轮换；多个标签页也需要协调。页面重载会清空内存 Access Token，可在启动时尝试一次会话恢复。刷新接口自身失败时不能再次触发自动刷新。自动重试还须考虑请求体能否复用、写操作是否需要幂等键。

    退出登录需要前后端共同处理

    1. 前端调用 POST /auth/logout，按上述方式附带刷新 Cookie，后端检查来源及 CSRF 防护。
    2. 后端撤销对应刷新会话，并通过 Set-Cookie 删除相同名称、Path 和 Domain 范围的 Cookie；本例没有设置 Domain。
    3. 前端清空内存 Access Token，切回未登录界面。退出接口网络失败时，不能把服务端会话视为已成功撤销。
    Set-Cookie: refresh_token=; Max-Age=0; Path=/auth; HttpOnly; Secure; SameSite=Strict

    旧 Access Token 是否立刻失效？如果后端只验签和有效期，已签发的访问令牌仍可使用到过期。要支持“立即退出”“强制下线”，还需在请求时查询撤销列表、会话状态或令牌版本等共享状态。只删除浏览器里的令牌，无法让其他地方持有的副本自动失效。

    07 / FRONTEND EXAMPLE

    前端代码：登录与携带 Bearer

    下面展示基础请求路径。API 地址、接口和错误码均对应本文示例；自动刷新需要再加入上一节的并发控制、CSRF 约定和重试规则。这段代码不会由文档自动执行。

    const API = "https://api.example.com";
let accessToken = null; // 当前页面内存

async function login(username, password) {
  const response = await fetch(`${API}/auth/login`, {
    method: "POST",
    credentials: "include", // 使用刷新 Cookie 的跨源方案需要此项
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ username, password })
  });

  if (response.status === 401) throw new Error("账号或密码错误");
  if (!response.ok) throw new Error("登录服务暂时不可用");

  const data = await response.json();
  accessToken = data.access_token;
  return data.user;
}

async function getArticles() {
  if (!accessToken) throw new Error("请先登录或恢复会话");

  const response = await fetch(`${API}/api/articles`, {
    headers: { Authorization: `Bearer ${accessToken}` }
  });

  if (response.status === 401) {
    // 根据错误约定尝试刷新一次，或通知用户重新登录。
    // 此处不直接递归调用，避免刷新失败时形成死循环。
    throw new Error("登录状态无效，请刷新会话或重新登录");
  }
  if (response.status === 403) throw new Error("没有访问权限");
  if (!response.ok) throw new Error("读取文章失败");

  return response.json();
}

    浏览器不会自动把 JSON 响应中的 JWT 变成 Authorization 头，前端需要显式添加；Cookie 才由浏览器按规则自动管理。前端可以读取 exp 提前安排刷新或调整界面，但是否放行始终以后端校验为准。Fetch 网络异常、CORS 拦截与 HTTP 401 是不同情况，不能一律当作登录过期。

    08 / STORAGE

    令牌放在哪里，决定了它如何发送

    位置发送方式特点与边界
    JavaScript 内存前端主动加入 Authorization页面重载后丢失；不持久保存，但页面中的恶意脚本仍可能读取令牌或发起请求。
    localStorage / sessionStorageJavaScript 读出后主动加入请求头localStorage 可跨重载保存；sessionStorage 通常随标签页会话结束而清除。两者都可被同源脚本读取，XSS 可窃取令牌。
    HttpOnly Cookie浏览器按域、路径、SameSite 等规则附带JavaScript 不能直接读取；依赖 Cookie 自动认证的接口需要 CSRF 防护，仍要防范 XSS。

    本文示例选用内存 Access Token + HttpOnly Refresh Cookie。也可以采用其他架构，例如全部使用 Cookie，或由后端代理持有令牌；这会改变浏览器携带凭据的方式。JWT 不要求必须使用 localStorage。OWASP 浏览器存储 ↗

    针对 Cookie 认证的刷新、退出和登录等接口，应按部署方式校验可信的 Origin / Referer，并采用合适的 CSRF 令牌或其他防护。SameSite 是一层防护，不能代替完整设计；“同站点”范围也可能大于“同源”范围。OWASP CSRF 防护 ↗

    09 / CORS

    跨域时，浏览器可能先发一条 OPTIONS

    前端和 API 的协议、主机或端口任一不同，就是跨源。例如 admin.example.com 请求 api.example.com。跨源请求使用 Authorization 或 JSON Content-Type 时，浏览器通常会先发预检；预检结果可被缓存，因此并非每次都能看到 OPTIONS。

    OPTIONS /api/articles HTTP/1.1
Origin: https://admin.example.com
Access-Control-Request-Method: GET
Access-Control-Request-Headers: authorization

HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://admin.example.com
Access-Control-Allow-Methods: GET, POST, PUT, PATCH, DELETE, OPTIONS
Access-Control-Allow-Headers: Authorization, Content-Type
Vary: Origin

    预检用于询问“这个来源能否发送这种请求”，通常不携带用户认证凭据。服务端处理 OPTIONS 后，浏览器才发送真正的业务请求。CORS 中间件应先于 JWT 中间件执行，且 401、403 等实际响应也需要合适的跨域头。MDN CORS ↗

    如果跨源请求还要带刷新 Cookie

    前端设置 credentials: "include"；服务端在预检和实际响应中允许凭据，并返回明确、已验证的前端来源：

    Access-Control-Allow-Origin: https://admin.example.com
Access-Control-Allow-Credentials: true
Vary: Origin

    携带 Cookie 的跨源请求不能用 Access-Control-Allow-Origin: *。本文同站点部署可使用 SameSite=Strict；如果前后端真正跨站点，需要评估 SameSite=None; Secure、CSRF 防护和浏览器第三方 Cookie 限制，不能只添加 credentials 就假定一定可用。

    对应本项目：middleware/cors.go 已提前应答 OPTIONS，当前按开发期策略回显来源和请求头，尚未设置 Allow-Credentials。采用本文 Cookie 刷新方案时，需要先落实来源白名单，再允许凭据；允许的请求头也应明确约束。CORS 控制浏览器的跨源访问，不能替代身份认证或权限校验。

        └── JWT 中间件 → 可信用户上下文
            └── 业务权限 / 记录归属校验 → 文章、目录等处理器

    刷新接口不应以“访问令牌仍有效”为前提，否则访问令牌一过期就无法刷新；它依靠自己的刷新凭据校验。公开登录接口虽不要求 JWT，仍应有凭据校验、请求来源防护和必要的请求限制。

    模块负责什么
    配置与密钥管理可信算法、签发方、受众、访问时长、密钥读取与轮换；密钥不交给前端。
    登录 / 会话服务验证密码，签发访问令牌，创建并轮换刷新会话，执行退出。
    JWT 中间件提取令牌，验签与验声明，必要时检查撤销状态，将可信身份写入 Gin 上下文。
    业务处理器 / 权限服务按当前身份检查动作权限与记录归属，不因“验签通过”就允许所有操作。
    数据库 / Redis 等状态存储用户与密码哈希、刷新会话与其失效状态；按需求保存撤销列表或会话版本。
    11 / QUESTIONS

    几个容易混淆的问题

    JWT 的长度固定吗？可以像 MD5 一样用 CHAR(32) 保存吗？

    JWT 总长度不固定，会随声明数量、内容长度、算法和密钥类型改变。不能套用 MD5 的固定长度字段设计。访问 JWT 通常无需整串持久化；若业务确实要保存，应按实际最大长度和用途设计字段，并给接收端设置合理长度限制。刷新会话也可只存随机刷新令牌的摘要与会话元数据。

    既然 Payload 能看见，别人修改成管理员不就可以了吗？

    修改载荷会改变签名输入。对方如果没有签发密钥，就无法生成与新内容匹配的有效签名，后端验签应当失败。前端自行修改页面或隐藏按钮没有授权效力，权限必须由后端检查。即使把角色放进 JWT，它也只是签发时的快照；需要立即反映角色变化时，要查询当前权限或结合版本机制。

    为什么还需要 HTTPS？JWT 已经有签名了。

    签名用于检测篡改，通常不隐藏载荷，也不能阻止被窃取的 Bearer Token 被重放。HTTPS 保护传输中的账号密码、令牌和业务数据；它与 JWT 的作用互相补充。

    用了 JWT，是不是完全不用查询数据库？

    常见访问令牌可在本地验签，因此不一定需要先查数据库里的令牌记录。但用户状态、实时权限、业务数据、刷新会话以及立即撤销仍可能需要查询数据库或缓存。“无状态”通常描述一部分令牌校验过程。

    刷新令牌能否直接访问文章接口？

    不应允许。访问令牌与刷新令牌用途不同，要使用不同校验逻辑；本例业务接口仅接受访问 JWT，刷新端点只验证刷新会话。若两类令牌都使用 JWT，也应通过不同受众、类型或其他明确规则避免混用。

    签发密钥和用户密码是一回事吗？

    不是。用户密码用于登录认证，数据库保存专用密码哈希；签发密钥属于服务端，用于保护令牌。每个用户无需拥有一份 HS256 签发密钥，前端也不需要知道它。公钥可以公开，私钥或共享密钥必须保密。
