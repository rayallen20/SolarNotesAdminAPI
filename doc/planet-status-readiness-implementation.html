GET /v1/planet/status

天体创建状态与完整性检测

创建表单需要知道哪些天体还能补建，页面上的检测卡需要知道太阳和八颗行星是否齐全。这两个答案来自同一次天体查询。接口保留 data.planets 供表单使用，并在同一层新增 data.readiness 供检测卡使用。

前后端接口约定 · 现有查询 FindByNames · 现有路由与管理员鉴权

请求与响应

沿用现有 GET 路由，请求头携带 Authorization: Bearer <access_token>，无需请求体或查询参数。成功时 HTTP 状态和业务码均为 200。每次都按 biz.names 的顺序返回九项，每项保留原有的 name 和布尔值 exist。

readiness 字段取值规则
ready布尔值，缺失清单为空时为 true。
required_count整数，取固定名称集合的长度，当前为 9。
created_count整数，取九项明细中 exist == true 的项数。
missing_names字符串数组，依次列出 exist == false 的名称。返回原始英文标识，页面可据此显示中文名称。

业务层汇总一次查询的结果

在 biz/planet.go 中添加 PlanetStatus，表示一次检测的整体结果。将 (*Planet).ShowStatus 的成功返回值从 []*Planet 改为 *PlanetStatus。工程中该方法的调用方是本接口的控制器，现有 names、fillByORM 和文件导入均可复用。

用 FindByNames(ctx, names[:]) 取一次候选记录，按返回的原始名称建立索引。随后遍历 names，每次匹配同时决定明细和摘要。即使 MySQL 的排序规则让 sun 进入查询结果，Go 字符串键也只会将 Sun 判为命中。历史额外名称不会占用任何必需天体的名额。

空表查询成功时，上述循环仍会生成九条明细和九个缺失名称。查询出错则在生成摘要前返回错误，由控制器通知页面本次检测失败。天体检测只读取 planet 表现有字段，无需数据库迁移或额外的计数查询。

为完整性摘要定义响应 DTO

在 param/resp/v1/planet/show_status.go 中扩展 ShowStatusResp。Readiness 使用值类型，四个字段始终参与序列化；业务层初始化的空切片让齐全时的 missing_names 编码为 []。

控制器组装明细和摘要

替换 controller/v1/planet/planet.go 中的 ShowStatus。控制器接收业务结论，组装响应 DTO，再按 RespBody.Success(map[string]any) 的现有签名传入两个同级字段。可沿用当前文件的导入。

天体查询失败沿用业务码 10201，内部异常沿用 500。管理员令牌过期或无效由鉴权中间件分别返回 20003 或 20004。这些错误响应均沿用 HTTP 200 和空对象 data: {}。前端先判断业务码，只有成功响应中的 ready 可以作为检测结论。

联调与验收

在 Postman 选择 GET，请求 {{base_url}}/v1/planet/status，在 Authorization 下选 Bearer Token 并填入已登录管理员的令牌。对每份成功响应核对三件事：明细长度等于 required_count，created_count 等于明细中已创建项的数量，按明细顺序取出所有未创建项的名称恰好等于 missing_names。
