POST /v1/book/reorder

保存一个天体的完整书序

管理员选择天体后，页面从 book/options 取得整份书单。点击「调整书序」时保存原始 ID 序列，上下移动只改本地草稿，取消即丢弃。点击「保存书序」才提交原序列与目标序列。后端以数据库的当前顺序核对原序列，一次事务保存新顺序，并返回该天体的全部书籍。

书籍管理原型 · 前后端调序契约 · 创建书籍的天体锁 · 编辑书籍的行锁

契约与示例

沿用管理员 Bearer 鉴权，请求头使用 Content-Type: application/json。planet.id 与每个 books[].id 均为正 int64 的十进制字符串。两个 books 数组都包含全部显示和隐藏书籍。目标数组的第一项落为 sort = 1，依次直到 N。

成功响应中的 data.books 与 book/options 共用 respBook.OptionResp，按目标顺序返回字符串 ID、标题、实际序号及显隐。前端可直接替换该天体的列表。显式空数组表示空书单，成功响应为 {"code":200,"message":"success","data":{"books":[]}}。现有书籍摘要 DTO

请求绑定与排列校验

先判断请求能否表达一个合法的排列，再查它是否仍与数据库相符。操作对象为所选天体下的完整书单，全库分页的 book/list 无法用作快照来源。

示例判定结果
缺少 expected.books、传 null、元素无 ID、ID 为裸数字、非正数或溢出ShouldBindJSON 校验必填对象、数组和每项引用。10101
原序列为 A B C，目标为 B A、B A A 或 B A D目标有漏项、重复或引入新 ID，两个数组本身无法构成同一组书的排列。10101
两个序列都遗漏同一本隐藏书，或都含同一个外天体 ID输入可构成排列，锁内读出的成员与原快照不同。20203
两个数组都为空仍检查天体和数据库书单。天体存在且无书时返回空数组，有书时返回书序冲突。200 或 20203
核对两个序列的长度、唯一性与成员集合

在事务开始前将原始 ID 放入集合，再按目标顺序逐个移除。由于两个数组长度相同，移除时找不到 ID 就意味着目标重复或引入了新的书籍。长度检查也确保最终序号能由数据库的 INT UNSIGNED 表示。

锁定书单并核对快照

  1. 使用 READ COMMITTED 开启事务，按主键 FOR UPDATE 锁定一条 planet 记录。找不到天体返回 20102。锁顺序与现有 book/create 相同，即使天体此刻没有书，也能将追加与调序串行化。
  2. 按 planet_id 读取该天体所有书籍，使用 ORDER BY sort, id FOR UPDATE。同时读取响应需要的标题和显隐。只读的 OptionsByPlanetID 自己会开启另一个事务，此处使用当前 tx 完成锁定读取。
  3. 将锁内序列与 expected 比较长度和每个位置的 ID。有一项不同即返回 20203。即使目标恰好与数据库此刻相同，也先报告快照失效。
  4. 核对通过后保存排序。目标位置和持久化序号均一致时跳过更新。用锁内读取的最新标题和显隐组装结果，只在 Commit() 成功后交给调用方。
查看 model.Book.Reorder 事务入口

这套流程只需要现有的天体主键、书籍主键和 UNIQUE (planet_id, sort)。上线前可用 SHOW CREATE TABLE book 核对 sort 的 INT UNSIGNED NOT NULL 类型及联合唯一索引。现有创建、编辑和选项读取实现

在唯一索引下交换序号

以 A、B、C 的当前序号 1、2、3 为例，目标顺序是 A、C、B。直接将 C 改为 2 会撞上 B。先找一个当前天体未使用的合法序号，再按目标顺序填位置。每次只把一本书移入空位，刚腾出来的位置就能用于下一次换位。

事务内执行的动作ABC
按原序读入，找到空位 4123
给 C 腾出第 2 位，将 B 暂移到 4143
将 C 从 3 移到 2，得到空位 3142
将 B 从 4 移到 3，提交事务132

每次保存仅更新 book.sort。已经处理完的目标位置不会被后续步骤占用，因为每本书只出现一次。每个位置至多两次单行更新，每次检查影响行数。中途写入失败会回滚整个事务，包括暂移的那一本。

临时序号与边界。先从 1 查找首个空闲正序号，用 uint64 做上限判断，避免在 4294967295 处回绕。若所有正序号都已占用，已校验 N ≤ 4294967295，因此非负无符号列上的 0 必为空，可在事务内暂用。最终序号全部为 1..N。查找从 1 开始只经过已占用的连续前缀，即使有一条历史记录的序号很大，也无需按最大序号分配数组。

历史书序。此方案用 ID 序列核对快照，再逐项比较真实序号。如果数据库中 A、B 的序号为 0、3，而目标仍为 A、B，一次有效保存会将其整理为 1、2。新书追加的连续性检查和上线前对其他天体的历史数据整理仍按创建文档执行。

业务层、控制器与路由

biz.Book.Reorder 接收完整请求，把 ID 序列交给 model.Book，再把模型结果转成轻量业务实体。响应仅用书籍自身的字段，无需加载所属天体或目录。控制器以 OptionResp 组装统一响应，所有新业务码及响应方法仍放在现有 resp_body/resp_body.go。下列代码可使用各现有文件中的导入。

业务码前端处理

项目以 HTTP 200 承载已处理的业务结果。失败响应中的 data 为 {}。前端联调时在 API_CODE 登记 20203。

并发与联调验收

联调时先从 book/options 取得原序列，再用两条独立连接模拟管理员同时操作。成功后重新读取选项，并核对数据库中的 ID、序号、标题和显隐。

场景应观察到的结果
交换包含隐藏书的两项，或循环移动三本同名书200，按 ID 定位。返回顺序与 book/options 相同，只有书序改变。
空天体、单本书、顺序和实际序号均无变化合法快照成功。空数组输出 []，其余返回完整书单，均无需执行 UPDATE。
输入重复、两数组成员不一致、漏隐藏书、外天体 ID、天体不存在依输入与数据库核对的阶段分别返回 10101、20203 或 20102，两个天体的原序均保留。
两名管理员拿着同一原快照，保存不同的新顺序第一笔实际改序的事务提交后，第二笔取得锁发现原快照失效，返回 20203。
同一天体创建和调序同时发生若创建先提交，旧调序请求因少了新书返回 20203。若调序先提交，创建在新的完整书单末尾追加。
同一本书编辑标题或显隐，与调序重叠若编辑先提交，调序成功并返回新标题及显隐。若调序先提交，随后编辑仍能核对原字段并返回新的 sort。目录各节点状态保持原值。
已有 0、跳号或最大无符号序号，用准确快照提交按目标重新编号至 1..N。测试纯内存的空位选择时可用缩小的整数范围覆盖“所有正序号已用、0 空闲”。
在暂移成功后让下一次更新失败回滚后重新读取得到原书单，临时值不会被提交。不同天体同时调序时，各自核对自己的书单。
