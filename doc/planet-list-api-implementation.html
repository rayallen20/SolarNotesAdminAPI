01 / IMPLEMENTATION

接口约定与返回内容

GET/v1/planet/list

读取 planet 表中实际存在的全部记录，每条返回 id、name、title 和 intro。请求无需请求体，也没有必填查询参数；沿用 Authorization: Bearer <完整 JWT> 鉴权。

列表按照 biz/planet.go 中已有 names 的标识顺序展示，即从太阳开始，再按行星距太阳由近到远排列：

Sun → Mercury → Venus → Earth → Mars → Jupiter → Saturn → Uranus → Neptune

业务层直接遍历已有 names，确保它是排序规则的唯一代码来源。只追加已经创建的记录；例如数据库只有 Earth、Sun、Neptune，列表返回 Sun、Earth、Neptune，不补充缺失天体。记录的 ID 或插入先后不改变上述顺序。

当前创建 API 仅允许太阳和八大行星九种名称，且名称有唯一约束，因此正常业务数据量很小，本方案返回完整列表。查询不设置 LIMIT 9，也不按固定名称集合过滤；如果数据库存在 names 未定义的名称，同样保留，但放在已知天体之后，并按 ID 升序排列。将来扩展为大量天体时，可再增加分页契约。

追加 model.Planet.FindAll()

将下面方法追加到 model/planet.go。所需的 db、context 和 errors 导入均已存在。

追加完整方法model/planet.go 
// FindAll 本方法用于查询已创建的全部天体,按 ID 升序提供稳定的读取顺序
// 天体的展示顺序由业务层根据 names 决定
// 使用独立切片承接结果,不将接收者中已有的 ID 或名称作为查询条件
func (p *Planet) FindAll(ctx context.Context) ([]*Planet, error) {
	if p == nil {
		return nil, errors.New("nil planet model")
	}
	if ctx == nil {
		return nil, errors.New("nil planet query context")
	}
	if db.DB == nil {
		return nil, errors.New("database is not initialized")
	}

	planets := make([]*Planet, 0)
	err := db.DB.WithContext(ctx).
		Select("id", "name", "title", "intro").
		Order("id ASC").
		Find(&planets).Error
	if err != nil {
		return nil, err
	}

	return planets, nil
}

查询只读取响应需要的四列。模型使用固定的 id ASC 提供稳定读取顺序，供未知名称在列表末尾按 ID 升序展示。已知天体的最终顺序由业务层读取 names 决定，模型无需维护一份天体名称排序表。模型层保持没有 JSON tag 的设计；单数表名继续由数据库连接中的 SingularTable 配置确定。

结果写入独立的 planets 切片，接收者中已有的 ID 不会被带入查询条件。即使调用者复用一个已经填过字段的 model.Planet，也会读取全部记录。

这里使用 Find 查询集合。没有记录时属于正常结果，不转换为 PlanetNotFoundErr。First / Take 的“单条记录不存在”处理不适用于本接口。GORM 集合查询文档 ↗

04 / IMPLEMENTATION

追加 biz.Planet.List()

将以下方法追加到 biz/planet.go。所需的 model、sys_error、context、errors 和 fillByORM 都已经存在。方法返回业务实体切片，响应 DTO 的创建由控制器完成。

追加完整方法biz/planet.go 
// List 本方法用于查询已创建的天体列表,将模型记录转换为业务实体
// 已知天体按 names 顺序排列;其他名称保留在末尾,沿用模型的 ID 升序
// 空表返回空切片,不补充尚未创建的天体
func (p *Planet) List(ctx context.Context) ([]*Planet, error) {
	if p == nil {
		return nil, &sys_error.InternalError{
			Cause: errors.New("nil planet entity"),
		}
	}
	if ctx == nil {
		return nil, &sys_error.InternalError{
			Cause: errors.New("nil context"),
		}
	}

	orm := &model.Planet{}
	records, err := orm.FindAll(ctx)
	if err != nil {
		return nil, &sys_error.DatabaseError{Cause: err}
	}

	recordsByName := make(map[string]*model.Planet, len(records))
	for _, record := range records {
		if record == nil {
			return nil, &sys_error.InternalError{
				Cause: errors.New("nil planet record"),
			}
		}
		recordsByName[record.Name] = record
	}

	// 使用同一份 names 作为展示顺序来源,跳过尚未创建的天体
	orderedRecords := make([]*model.Planet, 0, len(records))
	for _, name := range names {
		record, exists := recordsByName[name]
		if !exists {
			continue
		}
		orderedRecords = append(orderedRecords, record)
		delete(recordsByName, name)
	}

	// 保留其他入口可能写入的未知名称,按原查询顺序放到末尾
	// 遍历 records 而非 map,确保这些记录也有确定顺序
	for _, record := range records {
		if _, exists := recordsByName[record.Name]; exists {
			orderedRecords = append(orderedRecords, record)
		}
	}

	planets := make([]*Planet, 0, len(orderedRecords))
	for _, record := range orderedRecords {
		// 每条记录使用独立实体,避免列表元素共享同一个指针
		planetBiz := &Planet{}
		planetBiz.fillByORM(ctx, record)
		planetBiz.Exist = true
		planets = append(planets, planetBiz)
	}

	return planets, nil
}

列表方法返回多条业务实体，不把整个列表塞入一个代表单条天体的接收者。它不修改接收者原有字段，因此不需要调用 flush。

先用 recordsByName 按名称建立索引，再遍历已有 names，将实际存在的记录追加到 orderedRecords。追加后删除对应索引，随后遍历原 records 把剩余未知名称放在末尾；这里不遍历 map 输出，因此顺序保持确定。数据库现有的名称唯一约束保证每个规范名称最多对应一条记录。

最后按照 orderedRecords 的顺序创建独立的 Planet，保证切片中的元素互不覆盖。Exist=true 仅用于保持业务实体语义一致；列表响应 DTO 不包含这个字段。

数据库错误先包装为 DatabaseError。异常的 nil 记录会返回 InternalError，而不是跳过后继续返回一份不完整的成功结果。空切片无需特殊报错，正常返回即可。

追加完整方法controller/v1/planet/planet.go 
// List 本函数用于处理天体列表请求,调用业务层并组装响应 DTO
func List(c *gin.Context) {
	respBody := &resp_body.RespBody{}
	planetBiz := &biz.Planet{}
	planets, err := planetBiz.List(c.Request.Context())
	if err != nil {
		var dbErr *sys_error.DatabaseError
		if errors.As(err, &dbErr) {
			respBody.DBError(err)
		} else {
			respBody.InternalError(err)
		}

		c.JSON(http.StatusOK, respBody)
		return
	}

	// 显式初始化空切片,确保没有记录时输出 [] 而非 null
	listResp := &respPlanet.ListResp{
		Planets: make([]*respPlanet.ListPlanetResp, 0, len(planets)),
	}
	for _, item := range planets {
		planetResp := &respPlanet.ListPlanetResp{
			ID:    strconv.FormatInt(item.ID, 10),
			Name:  item.Name,
			Title: item.Title,
			Intro: item.Intro,
		}
		listResp.Planets = append(listResp.Planets, planetResp)
	}

	respBody.Success(map[string]any{
		"planets": listResp.Planets,
	})
	c.JSON(http.StatusOK, respBody)
}

通过 errors.As 识别数据库错误后，将原始 err 传给 DBError；其余业务错误交给 InternalError。返回错误响应后立即 return，避免继续组装成功数据。

make([]*respPlanet.ListPlanetResp, 0, len(planets)) 创建了非 nil 切片，确保空结果编码为 []。使用 strconv.FormatInt 将每个 ID 转为十进制字符串；前端接收后也应保持字符串类型。

沿用原有 Success(map[string]any)：data 是对象，planets 是其中的数组，数组中的每项是天体信息对象。控制器不直接 JSON 序列化模型或业务实体。

注册位置保持在 router.Use(...) 之后。列表请求沿用全局管理员鉴权，免鉴权集合继续仅包含 POST 登录接口；不需要为 List 再注册一份鉴权中间件。

与当前前端列表的字段对应

当前 BodyListPage.vue 的表格以 id 作为 row-key，显示 name、title、intro；中文天体名称由前端固定配置根据 name 得到。这与本 API 的四字段结构对应。

前端 src/api/body.js 的 getBodyList() 目前仍是内存演示实现。后续接入真实接口时，应先判断统一响应业务码，再将 data.planets 提供给页面使用；不要把 HTTP 200 单独当作业务成功。

创建成功仍只返回 data: {}。页面可以在创建成功后重新请求 GET /v1/planet/list 刷新列表。本文提供后端实现方案，未修改前端调用代码。
