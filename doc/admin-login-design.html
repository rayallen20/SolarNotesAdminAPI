IMPLEMENTATION PROPOSAL / ADMIN LOGIN

管理员登录功能
实现方案

沿着 Controller → Biz → Model 的调用关系，把当前的参数绑定接口补充为能够验证管理员、签发 JWT 并记录当前令牌摘要的登录接口。

已按本次审阅意见修订Gin + GORM + MySQLPC 管理后台每账号一枚当前有效令牌

登录成功的条件是：请求合法、账号密码正确、JWT 成功生成，而且 JWT 的 SHA-256 摘要已经成功写入该管理员的 token_hash。满足全部条件后，再把完整 JWT 返回给前端。

本文是下一轮实现的设计依据。当前交付物为这份 HTML；文中的接口响应、函数签名和新增文件属于方案，不能据此认为登录代码已经完成。

01 / BASELINE

以现有代码和已确认的数据约定为基础

位置当前代码需要补充的行为
main.go已有 POST /v1/admin/login，先注册 CORS。沿用当前登录路由；接入启动时的 JWT 配置校验。
controller/v1/admin/admin.go绑定参数，失败时返回包装响应；成功路径打印账号和密码。调用业务层、组装响应；移除密码打印，补齐成功与失败分支。
biz/admin.go只有 Admin 数据结构。增加登录业务流程、凭据比较、JWT 签发及保存结果判断。
model/admin.go只有模型字段，尚无 GORM 列映射和查询方法。映射数据库列，按账号查管理员，按主键更新令牌摘要。
param/resp/v1/admin/login.go已定义 LoginResp.Admin 与 LoginAdminResp，令牌位于管理员对象内。直接沿用该响应结构，按 data.admin 层级组装。
resp_body/resp_body.go已有 Data map[string]any 与 Success(data map[string]any)，成功消息为 success。沿用包装器与参数类型，补充登录及后续鉴权错误；外部错误消息不直接拼接数据库内部错误。

已确认的数据约定

表名是 admin；账号列是 name，区分大小写；密码列保存已有 SHA-256 小写十六进制摘要；token_hash 保存当前 JWT 的 SHA-256 摘要，空字符串表示未登录。

本次拟实现的功能范围

完成登录接口、接入现有响应 DTO、模型查询与条件更新、JWT 与摘要工具、配置校验。本文同时给出后续鉴权中间件的过期响应约定；退出、改密和刷新令牌接口分别后续实现。

继续使用已有管理员记录。登录不创建管理员，也不重新生成管理员主键。雪花 ID 在 Go 内使用 int64，在响应和 JWT 的主体声明中转成字符串。

本次审阅已确认：前后端固定使用 Bearer；成功数据仅包含 data.admin 对象，内部为 id / username / access_token；有效期只由后端校验，前端收到过期响应后跳转登录页；Biz 接收完整请求对象；Model 沿用默认表名映射，仅保留 GORM 标签；包装器继续使用 map[string]any。

以下是待审阅的建议值：使用 HS256 签名，访问令牌有效期暂定 15 分钟；登录接口沿用当前的 HTTP 200 + 业务码风格。它们不是 JWT 强制规定，审阅后可以调整。

02 / API CONTRACT

接口路径与请求体沿用现有定义

POST/v1/admin/login公开登录接口 · Content-Type: application/json
请求示例 · 密码为用户输入的原文，正式部署通过 HTTPS 传输
{
  "admin": {
    "username": "admin",
    "password": "<用户输入的初始密码>"
  }
}
请求字段约束处理原则
admin必填、非 null，必须为对象。继续使用当前指针结构与 binding:"required"。
admin.username沿用必填、长度 5–20；建议另外拒绝全空白账号。保持大小写，不调用 ToLower；不自动改变账号内容。
admin.password沿用必填、长度 6–20。作为原始密码接收，不 Trim、不转大小写，不要求前端先计算摘要。

请求中的 username 与数据库中的 name 是不同层的名称。请求格式可以保留，模型用列标签映射数据库，不需要为此修改表结构。

继续使用 ShouldBindJSON，由 Controller 自行决定包装响应，避免绑定方法提前写入另一套 HTTP 错误格式。Gin 官方绑定说明 ↗

按本次约定确定的成功响应

HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: no-store

{
  "code": 200,
  "message": "success",
  "data": {
    "admin": {
      "id": "2119659239906480128",
      "username": "admin",
      "access_token": "<完整 JWT 字符串>"
    }
  }
}

前后端固定按 Authorization: Bearer <JWT> 通信。成功响应不额外返回令牌类型或到期时间，前端从 data.admin.access_token 取令牌，不解析 JWT 判断有效期，也不设置令牌过期计时器。JWT 内部仍保留 exp，由后端在每次鉴权时验证。

data 的直接子项全部是对象；本接口仅有 admin 这个直接子对象，账号信息与令牌放在该对象内部。数据库模型中的密码哈希和令牌摘要不进入响应。后续受保护接口发现过期时，按 第 07 节的过期响应约定 通知前端。

业务码与失败结果

本草案沿用现有登录 Controller 的 HTTP 200 风格；前端用响应体 code 判断业务结果。未命中路由、网关错误及网络故障仍按各自机制处理。

业务码情形对外消息 / 数据
200验证、签发与写库全部成功。message: "success"；返回 data.admin 对象。
10101，已有JSON 或参数校验失败。参数不合法；data: {}。
20001，建议新增账号不存在，或密码不匹配。统一“账号或密码错误”；data: {}。
20002，建议新增保存令牌前账号被删除或密码已变化，条件更新未命中。账号状态已变化，请重新登录；data: {}。
10201，已有数据库查询或更新失败。数据库操作失败，请稍后重试；data: {}。
500，已有随机值生成、JWT 签发或内部数据格式异常。服务暂时不可用，请稍后重试；data: {}。
HTTP 200

这是登录及后续鉴权协议的本地预览，不发送网络请求，不生成有效令牌。后续鉴权错误码为建议值。

03 / RESPONSIBILITIES

每层只承担清楚的一段职责

HTTP 请求
  → param/req/v1/admin.LoginReq       请求形状与长度约束
  → controller/v1/admin.Login        绑定完整请求对象，再传给 Biz
  → biz.Admin.Login(ctx, req)        读取请求中的账号密码，执行登录
  → model.FindAdminByName            按 name 查询数据库
  → auth                            SHA-256、JWT、随机 jti
  → model.UpdateAdminTokenHash       条件更新当前令牌摘要
  → param/resp/v1/admin.LoginResp    既有响应 DTO，令牌在 Admin 内
  → RespBody.Success(map[string]any{"admin": loginResp.Admin})
层负责数据边界
Controller参数绑定、调用 Biz、映射业务错误与响应 DTO。持有 Gin 上下文；不直接写 SQL、验密码或签 JWT。
Biz从完整请求对象读取账号密码，串联管理员查询、凭据验证、JWT 签发和摘要保存。接收 context.Context 和 *reqAdmin.LoginReq；返回业务结果或错误，不接收 Gin 上下文。
ModelGORM 列映射、查询和条件更新，返回执行结果。只接触数据库；不签发令牌，不使用 Gin。
Auth 工具摘要、随机 jti、JWT 签发与密码学校验。只处理传入的数据和可信配置，不直接访问数据库。
参数 / 响应层描述外部 JSON，隔离数据库模型与业务实体。请求密码仅在处理过程中短暂使用，响应没有密码或摘要字段。

按本次约定确定的业务入口

// biz：业务实体保留管理员身份，不长期保存原始密码。
type Admin struct {
    ID       int64
    Username string
}

func (a *Admin) Login(
    ctx context.Context,
    req *reqAdmin.LoginReq,
) (*AdminLoginResult, error)

type AdminLoginResult struct {
    ID          int64
    Username    string
    AccessToken string
}

reqAdmin 是 SolarNotesAdminAPI/param/req/v1/admin 的导入别名。Controller 绑定成功后直接把完整的 *LoginReq 传给 Biz，不再把账号和密码拆成方法参数。Biz 从 req.Admin 读取账号密码，对 nil 请求或 nil 管理员对象做防御检查；原始密码只在本次调用中使用。业务结果包含管理员身份与访问令牌，由 Controller 转成已有响应 DTO。

// c.ShouldBindJSON(req) 成功后：
adminBiz := &biz.Admin{}
result, err := adminBiz.Login(c.Request.Context(), req)
// 根据错误映射业务码；成功时转换为响应 DTO。
// req 包与 controller 包都叫 admin 时，使用 reqAdmin / respAdmin 导入别名。
04 / LOGIN FLOW

一次成功登录的处理顺序

  1. Controller 执行请求绑定与校验，失败直接返回 10101。
  2. Controller 将完整请求对象交给 Biz；Biz 从 req.Admin.Username 读取账号，再通过 Model 按 name 查询；不存在时返回统一凭据错误。
  3. 计算输入密码的 SHA-256，在 Go 中与数据库保存的摘要做恒定时间比较；不把原始密码带入 SQL。
  4. 读取可信配置，生成新的随机 jti，签发 JWT，计算这枚完整 JWT 的 SHA-256 摘要。
  5. 用主键和读取到的密码哈希作为条件保存新令牌摘要。数据库错误或条件未命中均不返回登录成功。
  6. 保存成功后返回业务结果；Controller 将 id、username、access_token 组装到 data.admin，调用既有 Success(map[string]any)，并设置 Cache-Control: no-store。
05 / DATA ACCESS

模型必须明确映射现有数据库列

当前 db.Connect 已启用单数表名，Admin 会对应 admin；但 Go 字段名与列名仍需单独处理。GORM 默认会把 Username 映射成 username，现有表中并没有这列。GORM 命名约定 ↗

model/admin.go · 建议映射
type Admin struct {
    ID           int64  `gorm:"column:id;primaryKey;autoIncrement:false"`
    Username     string `gorm:"column:name"`
    PasswordHash string `gorm:"column:password_hash"`
    TokenHash    string `gorm:"column:token_hash"`
}

沿用已启用的单数表名映射，模型不新增 TableName() 方法。模型不会直接进行 JSON 序列化，因此只保留 GORM 标签，不添加 JSON 标签。把模型中的 Password 改成 PasswordHash，表明读出的不是原文；主键和用户名由 Controller 转换到响应 DTO。现有日期默认值与 ON UPDATE 继续由数据库维护。

建议的 Model 方法

func FindAdminByName(
    ctx context.Context, username string,
) (*Admin, error)

func UpdateAdminTokenHash(
    ctx context.Context,
    id int64,
    expectedPasswordHash string,
    newTokenHash string,
) (updated bool, err error)

所有 GORM 调用传递 WithContext(ctx)。查询采用 Where("name = ?", username).Take(&record)，账号不存在时用 errors.Is(err, gorm.ErrRecordNotFound) 区分；其他数据库错误不能伪装成密码错误。GORM 单条查询 ↗

查询示意 · 参数通过占位符绑定
SELECT id, name, password_hash
FROM admin
WHERE name = ?
LIMIT 1;

保存新摘要时，检查密码是否仍为刚才验证的版本

查询账号与保存令牌之间，可能发生改密。为防止用刚失效的旧密码完成登录，建议采用一次条件更新：

UPDATE admin
SET token_hash = ?
WHERE id = ?
  AND CAST(password_hash AS BINARY) = CAST(? AS BINARY);

参数顺序：新 JWT 的摘要、管理员 ID、先前查询到的密码哈希。

最后一个条件只用于确认账号数据没有变化；密码是否正确已在 Go 中验证。二进制转换使这一条件按编码内容精确比较，不受该列不区分大小写的排序规则影响。若改密先提交，更新未命中；若登录先提交，后续改密再清空摘要，旧令牌仍会失效。

Model 检查执行错误及 RowsAffected，只有命中 1 行才返回成功。选择单列 Update，避免 Save 把旧模型的其他字段写回；需要写空字符串时同样显式更新单列，不能依赖会跳过零值的结构体更新。GORM 更新说明 ↗

并发登录规则：每次登录生成不同的 JWT。两个登录同时成功时，以最后一次成功写入数据库的摘要为准；较早返回的令牌也可能随即失效。这是“每账号一枚当前有效令牌”的预期行为。前端应避免重复提交；“仅 PC 使用”不会自动消除并发或多浏览器登录。

正常登录只更新该管理员的 token_hash，数据库自动维护更新时间。没有匹配记录时不创建账号，也不插入替代记录。管理员表结构在这轮方案中无需增加 token_version、刷新会话表或过期时间列。

06 / HASHES AND JWT

密码摘要与令牌摘要，输入和用途不同

数据生成方式保存位置 / 用途
密码摘要hex(SHA256(原始密码的 UTF-8 字节))，统一小写，64 个字符。admin.password_hash；登录时验证已有凭据。
访问 JWT包含声明，使用服务端密钥按 HS256 签发。完整值返回前端；后续随 Authorization 发送。
令牌摘要hex(SHA256(完整 JWT 字符串))，统一小写，64 个字符。admin.token_hash；判断该 JWT 是否为当前有效令牌。

这是对现有数据库与已确认规则的兼容设计：本轮沿用已有 SHA-256 密码数据，不进行密码算法迁移。摘要使用标准库 crypto/sha256 和 encoding/hex；验证时解码数据库摘要、检查长度，再用 crypto/subtle 比较。数据库中的损坏编码按内部错误处理。

不能混淆：JWT 的签名密钥属于服务端，既不是用户密码，也不是 password_hash 或 token_hash。知道密码摘要不能用于代替服务端密钥签发 JWT。两个数据库摘要都不返回给前端。

JWT 声明建议

{
  "sub": "2119659239906480128",
  "iss": "SolarNotesAdminAPI",
  "aud": ["SolarNotesAdminWeb"],
  "iat": 1900000000,
  "exp": 1900000900,
  "jti": "<每次登录重新生成的随机唯一标识>"
}
  • sub：管理员已有主键的十进制字符串，使用 strconv.FormatInt(id, 10)，避免前端 Number 精度损失。
  • iss、aud：服务端配置的固定签发方与使用对象，后续解析时必须匹配。
  • iat、exp：由同一次服务端取时生成，时间单位为秒；暂定有效期 900 秒。
  • jti：用 crypto/rand 生成 16 字节随机值后编码，每次登录生成新值；随机源失败则终止登录。不要依赖秒级时间戳来区分两次登录。

用 github.com/golang-jwt/jwt/v5 的注册声明结构签发，不自行实现 JWT 格式或验签算法；下一轮实现时核对并锁定具体依赖版本。JWT v5 文档 ↗

配置放在哪里

建议新增 conf/jwt.go，并在 conf.Config 增加 JWT 配置。示例 YAML 只描述公开参数：

jwt:
  issuer: "SolarNotesAdminAPI"
  audience: "SolarNotesAdminWeb"
  expire_seconds: 900

签名密钥建议从环境变量 SOLAR_NOTES_JWT_SECRET 读取，约定为随机密钥的 Base64 编码；启动时解码并要求至少 32 字节，禁止空值或静默使用示例密钥。HS256 的密钥长度要求见 RFC 7518 §3.2。编码只是便于配置，不增加密钥熵。

现有 YAML 加载启用了 KnownFields(true)，因此增加 YAML 键时必须同步增加结构体字段，并在 Config.validate() 中校验签发方、受众、正数有效期及密钥。配置不合法时应在启动阶段失败，而非等到第一次登录。

07 / AUTHENTICATION CONTRACT

令牌摘要只有参与每次鉴权，才能使旧令牌失效

下面是后续受保护接口必须接入的鉴权规则。登录接口负责签发和保存；鉴权中间件负责每次请求执行这些检查。只有登录接口、没有这一步，清空数据库摘要并不会自动阻止旧 JWT。

Authorization: Bearer <完整 JWT>
  → 检查格式与长度
  → 只允许 HS256，并使用可信密钥验签
  → 要求 exp，校验 exp / iss / aud，存在 nbf 时也校验
  → 验证 sub 是合法、正数的管理员 int64 主键
  → 查询该管理员当前 token_hash
  → 空字符串：拒绝
  → 与 SHA256(本次收到的完整 JWT) 不一致：拒绝
  → 身份认证通过，将可信管理员身份交给业务处理器
  → 业务处理器继续校验具体操作权限

JWT 解析配置应明确使用 WithValidMethods、WithIssuer、WithAudience 与 WithExpirationRequired。仅解析载荷、仅读取过期时间或调用不校验签名的解析函数，都不能视为认证通过。解析选项 ↗要求 exp ↗

后端判断过期，前端按响应结果跳转

前端只保存并发送令牌，不根据客户端时间判断 JWT 是否过期。后端在受保护接口鉴权时发现令牌过期，停止该业务请求并返回专门的业务错误。沿用 HTTP 200 + 业务码风格，建议预留以下错误码供后续鉴权接入使用：

建议业务码含义前端处理
20003已确认令牌过期。清理本地登录状态，跳转登录页。
20004令牌缺失、签名或声明无效、账号不存在，或数据库摘要为空 / 不匹配。清理本地登录状态，要求重新登录。
令牌过期响应示例 · 后续受保护接口
{
  "code": 20003,
  "message": "登录已过期，请重新登录",
  "data": {}
}

具体错误码是本文的建议编号，仍可调整；“过期由后端判断、前端收到对应响应后跳转”是已确认的行为。JWT 无效与 JWT 过期应区分，存在签名等其他校验错误时不应把它归类为单纯过期；数据库故障也不能伪装成登录过期。

没有发起请求时，前端不主动计时退出；下一次受保护请求得到上述响应后再跳转。后端不会因页面尚未跳转而放行过期令牌，也不会把过期请求继续交给业务处理器。

事件数据库操作后续请求的结果
首次成功登录保存 JWT A 的摘要。A 在有效期内且校验通过时可用。
再次成功登录用 JWT B 的摘要覆盖 A。A 不再匹配；B 成为当前令牌。
退出登录清空该管理员的令牌摘要。所有旧 JWT 在下一次鉴权时被拒绝。
修改密码在同一事务中更新密码哈希并清空摘要。所有旧 JWT 在下一次鉴权时被拒绝；旧密码不能重新完成登录。
自然过期不依赖数据库定时清理。即使摘要仍匹配，exp 检查也拒绝访问。

这里的“失效”指状态变更提交后，后续鉴权不再通过；已经完成鉴权并正在执行的请求不会被自动撤回。后续实现退出时，也要处理旧请求与新登录并发的顺序，避免延迟执行的旧请求覆盖新的会话状态。

当前方案每次访问读数据库中的摘要，先保持这个直接、可验证的行为；若以后加缓存，退出与改密必须同步使缓存失效。访问 JWT 不需要额外的 expire_time 列，也不需要新增版本号。

前端与跨域的衔接

前端在业务请求中主动添加 Bearer 头。当前 CORS 中间件已经先处理 OPTIONS，开发环境能回应 Authorization 预检；本草案不使用 Cookie 刷新机制，因此不要求为登录额外开启 Allow-Credentials。登录路由保留公开，不能先要求已有 JWT。

令牌在前端如何持久保存属于前端实现约定。本文后面的示例只在内存持有，页面重载后会丢失；如果需要刷新页面仍保持登录，应在审阅时说明，再单独确定存储方式。

前端如何判断登录成功

let accessToken = null;

async function login(username, password) {
  const response = await fetch("/v1/admin/login", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ admin: { username, password } })
  });

  if (!response.ok) throw new Error("登录服务请求失败");
  const body = await response.json();
  if (body.code !== 200) throw new Error(body.message);

  accessToken = body.data.admin.access_token;
  return body.data.admin;
}

async function requestProtected(path, options = {}) {
  const headers = new Headers(options.headers);
  if (accessToken) headers.set("Authorization", `Bearer ${accessToken}`);

  const response = await fetch(path, { ...options, headers });
  if (!response.ok) throw new Error("接口请求失败");
  const body = await response.json();

  // 与后端对齐后的鉴权业务码；不在前端解码 JWT 或判断时间。
  if (body.code === 20003 || body.code === 20004) {
    accessToken = null;
    // 实际前端若还保存了管理员信息或持久化令牌，也在此一并清理。
    window.location.replace("/login");
    throw new Error(body.message);
  }
  if (body.code !== 200) throw new Error(body.message);
  return body.data;
}

此处请求路径适用于同源部署或前端代理已转发到 API 的情况；前后端分离时使用配置中的 API 基地址。/login 是前端登录路由示例，实现时按前端实际路由调整。由于接口使用 HTTP 200 包装，仅检查 response.ok 无法判断业务是否成功，必须再检查业务码。网络和数据库故障单独提示，不统一当作过期处理。

11 / REVIEW POINTS

已确认约定与仍可调整的建议

账号列、现有密码摘要格式、每账号一枚当前令牌及退出 / 改密后的失效目标，继续沿用前面的讨论。本次修订已落实以下要求：

  1. 成功响应：code=200、message="success"；data.admin 内仅包含字符串 id、username、access_token。固定使用 Bearer，不额外返回令牌类型或到期时间。
  2. 有效期判断：JWT 内部保留 exp，完全由后端鉴权检查；前端收到专门的过期错误后清理状态并跳转登录页，不做客户端过期判断。
  3. 业务入口：biz.Admin.Login(ctx, req *reqAdmin.LoginReq) 直接接收完整请求体对象。
  4. 模型：使用当前单数表名策略，省略 TableName 方法；仅保留必要 GORM 标签，模型不添加 JSON 标签。
  5. 响应 DTO 与包装器：沿用已存在的 LoginResp / LoginAdminResp；Data 与 Success 均保留 map[string]any，其直接子项为对象。

  • HS256、后端有效期暂定 15 分钟；密钥由环境变量提供，YAML 管理公开参数。
  • 后续鉴权的过期码暂定 20003，无效 / 已撤销令牌码暂定 20004；行为确定，具体编号可调整。

  • 前端是否在刷新页面后保持登录仍待明确；本文示例使用内存，未引入刷新令牌、Cookie 或自动续期。
